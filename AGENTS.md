## Quirks

- The sdk from npm: every `package.json` pins the sdk's packages to exact npm versions from one release.
- Node 23 needs `--experimental-wasm-modules` for the hashing wasm (`@nori-zk/ethereum-tempo-proof-queue-utils-glam`); the test scripts set it.
- Toolchain: Foundry with `anvil --network tempo` (chain 31337, unlocked dev accounts holding pathUSD). That's what the tests ran on.
- Tempo has no native gas token: every account that sends a Tempo transaction (deployer, keeper) pays its fees in a USD TIP-20 (pathUSD on Moderato, from the faucet).
- A local node's clock only moves forward. Tests that move it run from an `evm_snapshot` and `evm_revert` to it; the Kelp replay vectors start in 2030 for that reason.
- The keeper signs through its own Ethereum and Tempo clients (ethers) and reads proof requests and Nori's state through the sdk's `createConnections`. The sdk's requests have no timeout, so the keeper caps each read. Its providers cache no request (`cacheTimeout: -1`), so each transaction reads its account's current nonce on Tempo's fast blocks.
- A Hardhat fork's clock lags real time. Align it (`evm_setNextBlockTimestamp`) before testing guards, or no supply checkpoint falls in the window.
- Config: one root `.env` (`.env.example`) for Hardhat, the ethereum and tempo scripts and the keeper; deploy outputs land in `ethereum/.env.nori-eth-*` and `tempo/.env.nori-tempo-*` (`scripts/deploy-moderato.sh`). The shell environment wins over both; `dry-run.sh` blanks the queue settings so it never uses yours. `web/.env` is different: it holds public build constants only, is committed, and must never be gitignored, deleted or replaced with a `.env.example`.
- Dry run of the whole loop without a prover: `scripts/dry-run.sh [--eth-rpc URL] [--tempo-rpc URL] [--yes]`. It uses ports 18545/18546 and a temp dir. Deploy outputs go to `NORI_ETH_ENV_DIR` and `NORI_TEMPO_ENV_DIR` when set.

## Rules that bite

- `NoriSnapshot` storage: `commitments` at slot 0, `snapshotCount` at slot 1.
- Result leaf = `sha256(0x00 ++ queryId ++ result)`. Never drop the `0x00`: without it a forged result can pose as a tree node (regression test in the vectors).
- Snapshot indices start at 1, and time keys are never zero. The reader rejects zero keys.
- The committed word is `root | 1<<255`. Readers reject words without the top bit.
- `NoriSnapshot.sol`, `snapshotProof.ts` and `NoriRead.sol` must hash identically; the tests pin them together.
- Every Solidity constant has a TS mirror in its contract's `<Contract>.const.ts` (`ethereum/contracts/`, `tempo/contracts/`, and the sdk's), exported from the package. Tasks, tests and the client import those; never copy a value.
- Tests and the fake prover plant committed batches into the Nori bridge's storage with `anvil_setStorageAt`, using the sdk's layout constants (`PACKED_STATE_SLOT`, `PROOF_QUEUE_BATCHES_SLOT` and their offsets).
- A guard pins its Nori bridge, NoriSnapshot, queries and intervals at `createGuard`. Changing any of them means a new guard.

## Conventions

- Follow the conventions already in use; don't invent new ones. Before choosing a structure, config, script, dependency layout or API usage, find how this repo, nori-tempo-sdk, yaw ([yaw-example](https://github.com/yaw-rx/yaw/tree/main/packages/yaw-example)) or ystate ([studio](https://github.com/yaw-rx/ystate/tree/main/packages/studio)) already does it, and do the same.
- Build, test, typecheck, lint and format only through the npm scripts (root and per package). Never call `tsc`, `eslint`, `prettier`, `vite`, `jest` or `hardhat` directly: the scripts carry the flags, configs and env files each package needs, and a bare `tsc` in a `web/` package writes `.js` into `src/`.
- Follow nori-tempo-sdk: npm workspaces, `@nori-zk/*`, Hardhat 3, tests on `anvil --network tempo` with the real verifier and tokens, never mocks.
- Root `package.json` lists every workspace by its path (`"web/apps/prove-balance"`, not `"web/apps/*"`), in build order (libraries before the apps that use them). Root scripts run a script across them with `--workspaces --if-present`; a new package picks them up by defining the script.
- Keep docs short. Prefer a diagram in `docs/` over prose.
- What this repo needs from the sdk goes through the sdk's change procedure (its AGENTS.md): one request covering everything, the user approves, commits and publishes; then bump the pins here.

## Lessons

jk89 was sad the agents ignored his abstraction and worked around it

- The sdk's connection layer and machines exist so that no app handles connectivity itself. Read the sdk's own Lessons (its AGENTS.md) first; use what it exports and never work around it. What it lacks is added to the sdk, not written in an app.
- Apps compose observables only: the sdk's machines' `state$` and live streams. No `await` of a read, no promise read once, no `catchError(() => EMPTY)`. Every value that can change stays current; nothing is read once.
- The graph is the program, not a diagram of it. A machine gives every state a node, puts data only where it is valid, makes failures and lost connections states it recovers from, and cancels a read when its node is left. That holds only while every read, send and wait in the app goes through a graph: one `from(promise)`, `await` or `catchError` in a component or service brings back a state nobody designed. A value with no machine gets one (in the sdk when it is read through the connections); the code never goes around the graph.
- Machines are isolated by domain: each holds only its own domain's states. One machine uses another by gating its own transitions on the other's `state$`, as the ystate README shows: the heater's transitions gate on `temperature$` (the physics example, "Coupled systems"), and Payment's `pay` gates on `deps.auth.state$` (the auth example, README "Quick look" and the studio's checkout workspace, `default-workspaces.ts`). A graph can also spread another graph's nodes and edges into its own (`...readThroughConnectionsOf(...)`). Never copy another machine's states into your own data.
- A machine describes one domain; everything else is the outside world, which it reaches only through `$`. Fixed configuration is not input: an address or an RPC URL known when the machine is made defines the machine. What arrives or changes during its life (data, another machine's state, the user, the chain) comes in through `$`, and the graph shows three things for it: the input arriving through `$`, an edge that fires only when the outside allows it (the gate), and the node the machine waits in until it does. That node is usually the one the gated edge leaves from: the heater waits in `idle` until `belowLowerLimit` lets it through, and Payment waits in `checkout` until `payRequest` brings the card. A node of its own is needed only when why it waits is something the domain shows or handles: Payment's `notLoggedIn`, which the user sees and `dismiss` leaves, or `waitingForConnectionWhile…`, which names the chain it waits on. A gate either waits or refuses: a filter in `$` waits silently (the heater's thresholds), an error edge refuses explicitly (`pay` errors into `notLoggedIn`); it refuses when the outside saying no is a state of the domain. Without these, the dependency is handled in code around the graph, and the graph no longer describes what the machine does.
- Connection state is shown in one place, the pins along the bottom (`libs/ui`), from the app's own connection config: green connected, blue unsure (no outcome yet, or the first failure in a row), red not connected. A wallet pin only where the app configures a wallet, last. Rules like this live in the shared library, never inline in a component.
- No errors in rows, tables or lists, and no raw error text anywhere: views show the machine's state in plain words, and the machine retries by itself.
- A read-only app (the bridge dashboard) reads through public RPCs and has no wallet. A wallet is only for an app that sends transactions.
- Test the unhappy path before showing anything: `npm run dev:local`, then `npm run outage -- eth|tempo down|up`, no wallet, the wallet on the wrong chain.
- Code is never copied: the second time the same code appears, in a machine, a service or a component, it is abstracted into one place every user calls (an sdk machine, or `libs/ui`).
- Finding a shortcut means searching the whole codebase for the same pattern and fixing every instance.
